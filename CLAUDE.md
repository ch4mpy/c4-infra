# CLAUDE.md

c4-infra: the infrastructure the c4-soft applications share on one machine (development workstation, demo VPS). [README.md](README.md) holds the design, the port registry and what an application provides; [docs/migration.md](docs/migration.md) how a former project moves onto it.

The demo host only shows use cases: it never hosts an acceptance-testing campaign, and can be reset at any time, redeployed from scratch with the applications' test data (README, "Demo host"; product owner, 2026-10-30).

## Repository layout

- Intent home: `docs/intent/`, one sub-folder per change (`NNNN-<slug>/`), see [docs/intent/README.md](docs/intent/README.md).
- One stack at the root for both environments: the compose base `compose.yml` with `compose.dev.yml` (workstation, `up.sh`) or `compose.demo.yml` (demo host), named by `COMPOSE_FILE` in `.env`; the shared Caddy configuration `caddy/` (`env/dev.caddy` or `env/demo.caddy`, picked by `INFRA_ENV` in `.env`); `register-app.sh`, which generates each application's site with `routes.sh` from its routes file (`examples/routes/`) and its `registry.txt` entry.
- `keycloak-import/` holds the realms the stack imports itself, once, at a start (`master`, and the simulated providers' `simulated-google`, `simulated-facebook`, `simulated-apple`: README, "Simulated social providers").
- `demo/` holds the demo host's scripts (`write-env.sh` on the workflow's runner, `deploy.sh` and `backup.sh` on the host, `vps-bootstrap.sh`); `.github/workflows/deploy-demo.yml` sends the files of `demo/deploy-files.txt`.
- The two images built here: `keycloak/` (Keycloak, pinned, its features, and the stack's login themes `keycloak/stack-themes/`, a theme JAR) and `reverse-proxy/` (Caddy with its rate-limit module); in dev `up.sh` builds them (`KC_IMAGE`, `PROXY_IMAGE` in `.env`), the demo workflow pushes them to GHCR tagged by the content of their directory, Keycloak's also `<version>-<tree>`, in a package its owner makes public once (`docs/demo-setup.md`, step 7). `keycloak-image.properties`, beside `keycloak/`, describes it for applications' tests: a change of `keycloak/` changes it and adds a changelog entry (README, "Keycloak in an application's tests"; `tests/0029-description.sh`).
- Scripts run under Git Bash on Windows and bash on Ubuntu: container paths need `MSYS_NO_PATHCONV=1`, host paths given to the docker CLI need `cygpath -w` under Git Bash, and so does a host path given to another native program (`jq`, `curl`, `git`, `openssl`…) while `MSYS_NO_PATHCONV=1` holds, unless it reads the file through a redirection (`jq … < "$file"`); no password goes on a command line. Under Git Bash, a CR written as an ANSI-C quote (`$'\r'`, `$'\x0d'`, `$'\015'`) inside `$(…)` or `<(…)` is dropped (hold it in a variable set outside), and `grep` sees a CR before LF only with `-U`. The tests sort with `LC_ALL=C sort`, whatever the workstation's locale (`tests/0019-collation.sh`).

## Verification

The proof of a change before review is `bash tests/run.sh --changed --all`, with the dev stack running (`bash up.sh`) and `jq` installed: every test the change concerns since the base branch, the `*-facts.sh` ones (Keycloak's and Caddy's behaviour, in throwaway containers) and the `*.stand-in.sh` ones (a stand-in demo host, `tests/lib/stand-in-host.sh`: a privileged Ubuntu container running its own Docker, whose volume keeps the pulled images) included. `bash tests/run.sh --all`, every test (about half an hour with two stand-in lanes), runs at the milestones the product owner sets: once a batch of intents is merged, before it is pushed, and before a release (product owner, 2026-10-28). `bash tests/run.sh` runs every test but the stand-in and facts ones. For an intermediate check, `bash tests/run.sh --changed [<base>]` runs only the tests the changes concern, the stand-in ones aside: committed since `<base>` (`origin/main` by default; `HEAD` for a step not committed yet), staged, unstaged and untracked. Each test's duration follows it, the slowest are listed at the end.

Each test declares what it covers in its header, e.g. `# covers: routes.sh registry.sh examples/routes/ tests/fixtures/0003/` (paths, a trailing `/` for a directory, globs; several lines allowed); a test covers its own file. A change to `tests/run.sh`, `tests/lib/` or a file no test declares runs every test; `docs/intent/` concerns none. A run refuses a tracked script no test declares (`uncovered: <script>`) before any test: a new script comes with a test that covers it.

A run whose tests include stand-in ones runs them in lanes, beside the others: lane 1 runs every other test, one after the other; the stand-in tests run on two stand-in hosts (`c4-infra-stand-in` and `c4-infra-stand-in-2`, each with its own volume), split by the durations of earlier runs (`c4-infra-test-durations` in the git directory). The run prints each test's start (`== <test> started (lane <n>…), its output in <file>`), then its output whole when it ends; Ctrl-C stops every lane. Two stand-in lanes need Docker Desktop given at least 10 GiB (Settings, Resources); with less, the run says so and uses one.

One run at a time per Docker: the runs that wait take the lock in the order they arrived, the skills' runs included once their copy of `tests/lib/suite-lock.sh` follows (their intent 0119). A waiting run names the holder's worktree and start time (`waiting for the run of …`) and its place (`place in the queue: <n>`, 1 when it is next); stopping it takes it out of the queue. A run frees the stack however it ends; `docker rm -f c4-infra.suite-lock` frees it from a run that hangs.

Prerequisites beyond the stack: Faito registered from `../faito` (its `deploy-dev.sh`), which several tests use as the sample application; with Docker Desktop, a `TMPDIR` it shares (e.g. `mkdir -p ~/.cache/c4-infra-tests && TMPDIR=~/.cache/c4-infra-tests bash tests/run.sh`), since the tests bind-mount their `mktemp` directories and `/tmp` isn't shared by default.
