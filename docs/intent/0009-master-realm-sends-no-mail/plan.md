## Starting point

- Keycloak 26.7.4 (`keycloak/Dockerfile`, `KC_VERSION=26.7`), started `start --optimized`, no realm import (`compose.yml`, service `keycloak`); its only mount is `./keycloak/themes/`.
- Known from Keycloak's docs: since 26.0, `--import-realm` imports the master realm when it doesn't exist yet instead of creating it; a realm that exists is skipped ("Import skipped"); import files may reference environment variables.
- The demo image's tag is the git tree of `keycloak/` (`deploy-demo.yml`): a file added under `keycloak/` changes the tag, rebuilds the image and restarts the shared Keycloak at the next deployment (what 0005 avoids). The import file goes **outside** `keycloak/`, in `keycloak-import/`.
- **To check first** (step 1, throwaway container, before any product code): (a) the placeholder syntax (`${VAR}` or `${env.VAR}`) that `start --import-realm` resolves; (b) a minimal master realm file with a user (realm role `admin`, `email`, `emailVerified`, a password credential from a placeholder) is imported on an empty database, and that user logs in with the admin CLI (password grant) while `verifyEmail` is on; (c) whether Keycloak still tries to create its bootstrap administrator from `KC_BOOTSTRAP_ADMIN_*` when the imported master realm holds that user (silently skipped, or a startup error); (d) a quoted `"true"` / `"false"` placeholder for `resetPasswordAllowed` becomes a boolean; (e) on that imported master realm, an administrator can create the registration account (`create-realm` role exists) and a realm, and the console's client exists; (f) restarted with a changed file, the master realm stays as it was (`--db=dev-file`: an in-memory database would be re-imported); (g) with `verifyEmail` on, the admin CLI login of a master user **without** an address (as `tests/0006-bootstrap-admin-replaced.stand-in.sh` creates `ops`) is refused or not; (h) a password holding `"` and `\` through a placeholder: the import works, or fails (placeholders replaced in the raw text); (i) `get realms/master` of a master realm Keycloak creates itself, compared with the imported one: the values Keycloak sets only when it creates it (`displayName`, `accessTokenLifespan` 60, `accessCodeLifespan` 60…) go into the file, so that only REQ-1's settings differ. If (b) or (e) fails: stop, record it, spec v2 (PA-1's decision can't hold). If (c) errors: Keycloak's container no longer gets `KC_BOOTSTRAP_ADMIN_*`, the import reads the same `.env` values under other names (a deviation). If (d) fails: an unquoted placeholder (the file is no longer plain JSON; tests substitute before `jq`). (g) decides the change to the 0006 stand-in test below; (h) decides `demo/write-env.sh`'s refusal.

## Risks

- Keycloak's master import behaves otherwise than documented (temporary administrator, roles, placeholders, booleans) → step 1 before product code; fallbacks and the spec-v2 stop in *Starting point*.
- A password with `"` or `\` might break the JSON at import, Keycloak failing its first start → step 1 (h) settles it; if so, `demo/write-env.sh` refuses it by name (a demo secret already holding one would fail the next deployment, saying which); dev's values are fixed (`env.sh`).
- *Verify email* refuses the admin CLI to a master user without a verified address → step 1 (g); `ops` in the 0006 stand-in test gets a verified address; the README says it for any new administrator.
- An imported master realm differs from one Keycloak creates (token lifespans, display name) → step 1 (i) copies those values into the file.
- Changing `MAILPIT_SMTP_PASSWORD` or `INFRA_HOST` now recreates Keycloak's container → said in the README and `docs/demo-setup.md`.
- The compose change recreates Keycloak's container (dev at the next `up.sh`, demo at the next deployment): one restart → the user is asked before step 2's `up.sh`; on the demo host no application is registered yet.
- Existing stacks keep their master realm (decided): the current demo host needs the documented re-creation once, after delivery (Stage 5, the operator's step); this workstation's re-creation (step 6) wipes Faito's realm and disturbs the faito session → announced first, Faito re-registered at once by `bash ../faito/deploy-dev.sh`.
- Both passwords sit in Keycloak's container environment (`docker inspect`) → accepted by REQ-6, as Mailpit's container already holds the SMTP one.
- Test mails pile up in the workstation's Mailpit → each test deletes the message it found (Mailpit API).

The import file carries that user profile (component `declarative-user-profile`) besides `displayName`, `displayNameHtml` and `accessTokenLifespan` 60. Within step 1 (i)'s scope; no other file.
- 2026-10-23 — step 1, fact (a): the placeholder syntax is `${VAR}` (`${env.VAR}` isn't resolved). Fact (d): a quoted `"true"` becomes a boolean: the file stays plain JSON.
- 2026-10-23 — step 1, fact (g): an administrator without an address still logs in with the admin CLI under *Verify email*: `tests/0006-bootstrap-admin-replaced.stand-in.sh` stays unchanged (its row in *Files* drops).
