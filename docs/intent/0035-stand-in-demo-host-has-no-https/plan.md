- **Every reload reads `/etc/caddy/Caddyfile`**: `register-app.sh:511-512` (`caddy validate` then `caddy reload --config /etc/caddy/Caddyfile`), `demo/deploy.sh:57` (after `up -d --wait`, `:53`). The container sees the stack's `caddy/` read-only at `/etc/caddy/` (`compose.yml:68`), its data in `caddy_data:/data` (`:69`). So a wrapper started with `caddy run --config <elsewhere>`, as `tests/0003-demo-edge.sh:66` and `tests/0015-headers.sh:70` do, is gone at the first reload.
- **The Caddyfile's first token is an import**: `caddy/Caddyfile:7`, `import env/{$INFRA_ENV}.caddy`, before any snippet or site. Relative imports resolve from the importing file's directory (Caddy's docs: "always relative to the file the `import` appears in"; `resolveImportGlob` in `caddyconfig/caddyfile/parse.go`). In `addresses()`, a top-level `import` splices the file's tokens and parsing goes on: a spliced `{` opens a block with no key, which the HTTP adapter takes as the global options block if it is first (read in the source, not documented: step 0 (e) measures it). `caddy/env/demo.caddy:5-6` leaves `env-tls` empty: Let's Encrypt.
- **`local_certs`** "causes all certificates to be issued internally by default"; **`skip_install_trust`** "skips the attempts to install the local CA's root into the system trust store" (Caddy's global options). Both are global options, so a site-level `tls internal` in `env-tls` wouldn't do: the root's installation would still be tried.
- **The root**: the community-documented path is `/data/caddy/pki/authorities/local/root.crt` (the image's `XDG_DATA_HOME=/data`); step 0 (a) confirms it. The admin API's `GET /pki/ca/local` returns it as `root_certificate`, but "if the requested CA ID is the default (`local`), then the CA will be provisioned if it has not already been" (Caddy's API docs).

## Risks

- **The wrapper relies on `Caddyfile:7` being the first token, and on a keyless block spliced by a top-level import counting as global options** (read in Caddy's source, not documented). → Step 0 (e) measures it; `tests/0035-stand-in-proxy.sh` fails in seconds if `caddy/Caddyfile` or Caddy changes either, in every `bash tests/run.sh`; a second global block makes Caddy refuse to start ("must be the first block"), never a silent fallback to Let's Encrypt.
- **A mount over a file is dropped when the host replaces that file** (rsync, tar: every redeployment that changes it). → The wrapper comes as a directory mounted over `/etc/caddy/env/`, a directory no deployment replaces; the stack's `demo.caddy` is read live through its own directory mount. AC-03 redeploys with replaced files; M4.
- **The stand-in drifts from the demo host beyond the issuer**, which every stand-in test relies on. → `tests/0035-stand-in-proxy.sh` compares the adapted JSON whole, but `apps.tls` and `apps.pki`.
- **Certificates are obtained in the background after a start or a reload** (inferred), so the first request after `sudo c4-app register` can fail its handshake. → `stand_in_https` waits for a verified handshake (C6). AC-01's system-store request runs after a verified one and expects exactly `60`, so a handshake not yet ready (`35`) can't pass for a refused trust.
- **curl given `--cacert` may still read its built-in CA directory.** → `--capath` points at an empty directory ("the default capath value is ignored"); AC-01 checks the `-v` lines; M3.
- **Caddy installs its root in its container's trust store** without `skip_install_trust` (IV-02). → The wrapper sets it; AC-06 checks the stores; M2 if step 0 (b) shows the install.
- **The authority's keys stay on the workstation between runs**: in the stand-in's `caddy_data`, inside the Docker volume `c4-infra-stand-in-docker`, until the next `stand_in_up` removes it, as a run's Keycloak database and passwords already do (spec PA-01's reading). → The header says so; nothing reads `root.key`; AC-06 checks the test's files and the uploads.
- **`stand_in_https` sends every host to the stand-in's Caddy** (C5 A): a test can't reach the internet through it. → Wanted on a stand-in (nothing reaches a public authority, RQ-02); the header says so.
- **Docker Hub from the stand-in fails now and then** (0020). → The fixtures' `caddy:2.11.4-alpine` is loaded from the workstation.
- **The skills' tests depend on the two functions' names, arguments and failures.** → The header is their contract (RQ-05); a later change breaks their tests, the signal 0095 PA-06 wants.
- **Time**: `--changed --all` is a full run here (`tests/lib/`), and the new stand-in test adds about 4 minutes to every full run. → Accepted; the fast test carries the configuration's quick feedback.
