## Problem

Every route to a front end (`fr`, `en`, `ui`) gets the single-page-app headers of the `spa-headers` snippet (`caddy/Caddyfile:22-28`, imported by `routes.sh:258-260`): a fixed Content-Security-Policy (`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`), `X-Frame-Options: DENY` and `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`. Caddy sets them before proxying and adds the upstream's own to them. Measured on 2026-10-26, with a throwaway Caddy 2.11.4 running the stack's `caddy/` and a site generated by `routes.sh`, in front of a stand-in that sends its own headers: the response holds two `Content-Security-Policy`, two `X-Frame-Options` (`DENY`, `SAMEORIGIN`) and two `Permissions-Policy`. A browser enforces every policy it receives, so an application's own policy can only restrict further, never allow what the shared one blocks.

immo (the immobilier.pf rewrite, about to register with the stack) needs what the shared policy blocks: map tiles from tile servers (its intent 0004), video frames (0005, 0027), Cloudflare Turnstile (0010), advertising frames (0026), and the inline scripts and styles of its server-side rendering. It means to allow them with its own policy, issued by its rendering server with a nonce per request and a versioned registry of third-party origins, tested with its code (immo's spec 0001, EX-18, CA-16, PA-07). Today its only ways are a weaker shared policy for every application, or a role of its own in the stack. immo's plan 0001 keeps its step 11 waiting for this change.

## Proposed outcome

An application's routes file may state, route by route, that a front end's Content-Security-Policy, X-Frame-Options and Permissions-Policy are the application's own. The browser then receives on that route exactly the headers the application sends, once each, while the headers every site gets (`common-headers`: `X-Content-Type-Options`, `Referrer-Policy`, no `Server`, HSTS on the demo host) stay. A route that doesn't state it keeps today's headers. The same in dev and on the demo host.

On such a route, a response without one of these headers (a static asset, an error page, the proxy's own 413 or 502) gets the shared value, as a default only: the proxy fails closed (product owner, 2026-10-27). An application that sends only `Content-Security-Policy-Report-Only` while it settles its policy therefore gets the shared policy enforced as well.

Success criterion: on such a route, a response carries a single Content-Security-Policy, the application's, unchanged; a route to the gateway, the MCP server or a redirect can't take the option, and a registration with it there is refused before anything changes.

## Affected users and systems

- Application (immo first), Developer, Demo visitor (on such routes, the protection of the application's pages becomes the application's own).
- Reverse proxy (`routes.sh`, `caddy/Caddyfile`), registration (`register-app.sh` generates each site with `routes.sh`, `sudo c4-app register` on the demo host), README ("Routes file"), tests.

## Constraints

- One origin per application (README, "Design"): an application's headers reach its own origin only, never another application's.
- 0003: dev and the demo host alike. Both generate the site with the same `routes.sh` from the same routes file (`INFRA_ENV` changes only its host name and upstreams); the proxy differs only by `caddy/env/*.caddy` (certificate, HSTS, RabbitMQ's UI).
- The routes file's rules: a line outside the notation is refused as `<file>:<line>: …` before anything is registered (`routes.sh:115-180`).
- 0013 reshapes `routes.sh` (each site written by `_routes_site`, the MCP server on an origin of its own): this change merges with it.
