## Engineer's choices

- Decided by Jérôme Wacongne (engineer), 2026-10-28: every recommendation below.

Proposed by Claude, to confirm with this plan:

- **The bound, imposed by a rewrite of the checked model** (`bound_logs`, `up` only, after `check_model`): `jq '.services |= map_values(.logging = $bound)'`, written to a new root-owned file and `mv`d, as `read_model` does. `check_model` runs on the application's model first, so it still refuses any `logging` of the application's. Rejected: a second compose file (`-f model.json -f logging.yml`: `c4-app` is a single installed file); the daemon's `log-opts` (PA-01 A, not chosen).
- **The value, a constant of `c4-app`** (`LOG_BOUND`, `json-file`, `max-size: "10m"`, `max-file: "3"`, strings as compose wants them), equal to `compose.yml`'s `x-logging`; the stand-in test compares an application container's `LogConfig` with a stack container's, so a drift fails. Rejected: `c4-app` reading `compose.yml`'s anchor (no YAML parser on the host; a `docker compose config` of the stack from a root command). **(to confirm)**
- **The retentions as flags in the `*_EXTRA_ARGS` of `compose.yml`'s base**: Loki `-compactor.retention-enabled=true -store.retention=336h -compactor.delete-request-store=filesystem`; `PROMETHEUS_EXTRA_ARGS: --storage.tsdb.retention.time=336h` (new); Tempo `-backend-worker.compaction.block-retention=336h`; Pyroscope `-retention-period=336h`. Rejected: adding `block_retention` to `grafana-lgtm/tempo-config.yaml` (one more difference from the image's file for 0007-lgtm's (d) to allow). **(to confirm)**
- **One spelling, `336h`**: Tempo's flag is a Go duration, without `d`; Loki, Prometheus and Pyroscope read `336h` too. The tests compare what each component prints (Loki's `2w`, Tempo's `336h0m0s`: recorded by step 1).
- **Pyroscope pinned too** (PA-04 Y: "if the plan finds a setting": `-retention-period`, its default 31 d), if step 1 shows it applies in the image's mode; otherwise the README records its default and nothing is set. **(to confirm)**
- **AC-03 on the stand-in by `c4-app` alone**: after `stand_in_accounts faito`, `$BEFORE`'s `demo/c4-app` (main's head at step 0, recorded in the test) replaces the installed one, Faito comes up unbounded, then the stack's `demo/deploy.sh` runs again as `c4-infra` (it installs this branch's `c4-app`, the rest unchanged) and Faito's same files come up again. Rejected: deploying the whole stack of `$BEFORE` first, as `tests/0016-simulated.stand-in.sh` does (two full deployments for a difference in one file). **(to confirm)**
- **AC-06's restart on the running dev `c4-infra.grafana-lgtm`** (`docker restart`, then healthy, then a log posted and read back), not a throwaway: it is what the developer runs; the facts test's throwaway restart measures the same before any change. **(to confirm)**
- One new stand-in test for every stand-in criterion (one stand-in deployment, about 7 min); 0007-compose-check's refusal list unchanged.

## Risks

- Compose doesn't recreate a container whose only change is `logging` → RQ-03 fails: step 1 (a) measures it, step 2's test proves it on the stand-in's compose (the demo host's version); fallback, a deviation: `up` recreates the services whose `LogConfig` differs, never all of them each time.
- Each application's containers restart once, at its first `up` after the deployment → expected (RQ-03); the README says so; no application runs on the demo host yet.
- A file that sets `logging` (Tickee's `x-logging` anchor) is refused → it already is (the generic line); the new message says why; docs/migration.md says to drop it.
- The bound's value written twice (`compose.yml`, `c4-app`) drifts → the stand-in test compares an application's `LogConfig` with `c4-infra.keycloak`'s.
- A wrong Loki flag stops Loki, and grafana-lgtm with it (`up.sh`, `deploy.sh` wait for it) → step 1 measures the flags on a throwaway first; `tests/0007-lgtm.sh` and step 3's test after.
- A setting the image accepts but doesn't apply (Tempo's backend worker not running in the single binary; Pyroscope's retention outside its mode) → step 1 checks the module runs, not only the printed config.
- The deletion itself isn't observed: Loki deletes no earlier than 24 h retention plus 2 h, Tempo and Prometheus on their own cycles → the proof is each component's effective configuration and its compactor running; the README states the settings.
- An image upgrade stops appending `*_EXTRA_ARGS`, or renames a flag → `tests/0026-stack-bounds.sh` reads the effective configuration and fails at that upgrade; the README says what to check.
- Dev keeps 14 days from the next `bash up.sh`: older dev telemetry is deleted at the first compaction → PA-04 (the compose base); the README says so.
- `docker compose -p <app> logs` run in `~/c4-infra` reads the stack's file under the application's name → the README says to run it from `~`, or `docker logs`; step 1 (b) measures it.
- The talker's 60 MiB on the stand-in's volume → bounded by the change, and removed with the containers at the next `stand_in_up`; the unbounded run before (AC-03) is recreated within the test.
