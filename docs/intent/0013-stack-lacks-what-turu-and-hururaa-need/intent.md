## Problem

Planning the migration of Tickee, Turu and Hurura'a onto the stack (2026-10-23) found what the stack and its guide lack for Turu and Hurura'a:

- **Keycloak's features.** Turu's AI agents act for a user through Keycloak's delegated token exchange ([Turu's decision 0011](https://github.com/ch4mpy/turu/blob/master/docs/decisions/0011-agents-attestes-par-la-delegation-keycloak.md), `keycloak/check-agent-delegation.sh`): two preview features, `token-exchange-delegation` and `parameterized-scopes`, that Turu's own Keycloak enables. The shared Keycloak enables none: on it, Turu's agents get no delegated token.
- **Keycloak's version.** Turu's and Hurura'a's own Keycloaks run 26.8.1, and Turu's realm is exported from it; the shared Keycloak runs 26.7 (26.7.4). Keycloak doesn't promise that a realm exported from a newer version imports into an older one.
- **An MCP server on the demo host.** Turu's first demo includes its MCP server (`/mcp`, `/.well-known/oauth-protected-resource/mcp`). On the demo host, a routes file naming the `mcp` role is refused, since no container port is fixed for an MCP server (README, "What an application's deployment does"): Turu's demo can't register.
- **The guide misleads.** `docs/migration.md`, which each project follows step by step:
  - says the REST API's Keycloak admin client is "unchanged in value", while the projects call the former Keycloak's own port (`https://${cn}:3643/auth`), which the stack doesn't serve;
  - says nothing of the organizations' `redirectUrl` in the realms, still on the former host;
  - moves the `openapi` profile's server port, not its management port: OpenAPI generation collides with a running application, or with another project's;
  - says nothing of certificates: the projects serve and trust a self-signed certificate of their own (copied into their jars, generated by their CI), not c4-infra's leaf and local CA as Faito does (`C4_INFRA_CERTS_DIR`), while Keycloak and the gateway call each other over TLS (back-channel logout);
  - doesn't say that `new-realm-ids.sh`, which gives each file ids of its own, breaks a reference from one realm to another's ids (Tickee's `federatedIdentities`);
  - gives Turu an `/assets/*` route its frontend doesn't use (Hurura'a's pf-ui does);
  - keeps notes that are no longer true: Turu's "uncommitted work", Hurura'a's export "step 5" (it is step 6), Faito's `faito.conf` transition (Faito 0021 is delivered: Faito registers `reverse-proxy/faito.routes`).

## Proposed outcome

- Turu's agent delegation works on the shared Keycloak, in dev and on the demo host. Success criterion: a client of a realm on the shared Keycloak obtains, by token exchange, a token delegated to it for a user (its `act` claim names the agent).
- A realm exported from a 26.8 Keycloak (Turu's) imports into the shared Keycloak. The master realm, Faito's realm and Tickee's realms keep their users, settings and sessions across the change, in dev and on the demo host.
- On the demo host, an application's routes file may name the `mcp` role, and its MCP server is reached on a container port the README fixes.
- The guide states each point above; the migration plans of Turu and Hurura'a follow it without correcting it.

## Affected users and systems

- Application (Turu and Hurura'a; Faito and Tickee, already on the stack, through Keycloak's change), Developer, Demo operator, Demo visitor.
- Shared stack (Keycloak), reverse proxy (`routes.sh`), demo host (`demo/c4-app`, `deploy.sh`), registration (`register-app.sh`), docs (`docs/migration.md`, README, `examples/routes/`).

## Constraints

- High-risk under the project's risk rules: authentication (Keycloak's version and features, shared by every application), what the demo host exposes (a new role routed to applications' containers).
- Keycloak migrates its database on the first start of a new version, with no way back but a backup.
- Faito and Tickee (migrated before this change) run on the stack meanwhile: their realms keep working.
- Preview features may change between Keycloak versions, and a feature is enabled for the whole server, not one realm.
